# ARC — Project Context

This file is the single source of truth for the ARC landing page project. It replaces the old `CLAUDE.md` (which only pointed here). Read this before making design or content decisions — it captures not just what exists, but *why*, including direction that was tried and explicitly rejected, so it doesn't get reintroduced by accident.

## What ARC is

ARC (formal name: **ARC Media**) is a founder-led creative content agency. Services: content calendar/strategy, scripting, videography, editing, and multi-platform social media management. The name is an acronym: **A**ttention, **R**etention, **C**onversion — that arc is meant to be the literal narrative structure of the page, not just a logo backstory.

- **Tagline:** "Stories that MOVE brands." — deliberate triple meaning: moves people emotionally, moves business metrics, and the agency's product is literally motion/video. "MOVE" is always capitalized when it appears as the emphasized word.
- **Target client:** personal brands, creators, and founders — not enterprise/corporate. Copy and trust-building should read peer-to-peer, not B2B-corporate.
- **Founder-led:** the brand has a real face/team behind it, not an anonymous agency — trust mechanisms (About/testimonials) should lean on that.
- **Proof position — CORRECTED 2026-09-03, read this carefully.** An earlier version of this file claimed ARC had a real client portfolio and real metrics and that the site should "lead with evidence." **That was wrong.** The user clarified: ARC has *not* worked with brands yet; it is an initial start as a brand. The founder does have real freelance work (scripting, shooting, editing) and real testimonials from it. The rules that follow are non-negotiable:
  - **Never invent a number.** No follower counts, view counts, engagement lifts, client counts, turnaround averages, or "X+ creators." If a figure isn't real, it doesn't go on the page.
  - **Never advertise being new either.** No "founding client," no "our first client," no apologetic framing. The site simply says nothing about tenure.
  - **Trust comes from craft, not results.** The page proves by showing the work and the thinking behind it. That is the single organising constraint for every section.
  - Sections removed for violating this: `ProofStrip` (deleted entirely — its three stats were invented) and the old `Portfolio`'s per-case metrics (rebuilt as `Work`, which carries *role* like "Script · Shoot · Edit", never an outcome).

## Visual identity

### ⚠️ Rebranded 2026-09-27: gold/black → "Signal"
The user reopened the brand (it is new and still being decided) and asked for a look that is **active, creative and professional**. Black-and-gold read as *luxury*, not *active*, so it was retired. The choice was made over ten rounds on a throwaway `/theme-variants` route (deleted afterwards), and each rejection is a rule:
- **Themes compared:** Signal (picked), Studio Paper (bone/ink/cobalt, editorial), Refined Gold (the old theme).
- **Accent:** the user kept Signal's orange-red after also seeing lime, cobalt, ultraviolet, mint and saffron.
- **Fonts:** Clash Display was "not that great"; **Geakosa** was the user's first wish but is personal-use-only, so free alternatives were compared and **Archivo** won.
- **Highlight word:** serif italic (Instrument Serif) → **rejected**; textured fills (grain, mosaic, LED pixels, halftone, dither) → **"no pattern needed in the text"**; brush/graffiti hands → **"very irregular"**; neat handwriting → superseded; **typewriter (Special Elite) with a capital first letter → picked**, thickened slightly (the user then asked for it thinner than first shown).
- **"Scene 01 —" numbering on section labels** was built and **cut by the user** ("looks a little off") — keep the section names only.

**Everything below this block that says "gold", "ivory" or "Satoshi" is history.** Read "gold" as *the Signal accent*, "ivory" as *bone*, and "GoldText" as *Highlight*. The rules about *where* the accent may appear (one word per headline, the action, the number that matters) still hold. The rules about *how gold looks* (gradients, champagne band, shimmer) do not.

### The accent: rules
- Flat colour, never a gradient on text. (The gold-gradient machinery existed because flat gold read as mustard; flat Signal doesn't have that problem.)
- **Allow-list:** primary CTA fills, the one highlighted word per headline, the proof numbers, the REC dot, progress/"you are here" marks (the Film/Work readouts, the HowItWorks playhead, the /book arc). Never nav hover states, never decorative borders or icons "because it looks nice". That dilutes the one thing the accent means: *this is the action / this is the thing that matters*.
- All highlighted words go through `Highlight` (or `TypedWord` for the Hero). Don't hand-roll a typewriter span elsewhere.
- Vendor logos in the toolkit card stay bone, never the accent (same reason as before: don't dress someone else's trademark in ARC's colour).

### Micro-interactions (added 2026-09-27)
Small feedback on everything you can touch, all driven by hover, press, focus or a one-time scroll-in, never a timer. Reduced motion is covered by the global CSS block, which flattens their transitions.
- **Focus:** one orange `:focus-visible` ring site-wide (`globals.css`). The site had no visible keyboard focus before this.
- **Press:** CTAs and pricing buttons scale to 0.97 on `:active`, and /book options to 0.99.
- **Lift:** pricing cards, review cards and the About bento cards rise 4–6px on hover, eased out (`cubic-bezier(0.16,1,0.3,1)`).
- **Founder portrait:** a slow 4% push-in on hover, like a camera easing forward. The REC dot in its frame is now Signal, not red-500.
- **FAQ rows:** the question slides 6px and the number and `+` brighten on hover.
- **Footer links:** `.link-draw`, an underline that draws in from the left.
- **Nav logo:** dims on hover.
- **Review stars:** fill in one after another, once, as each review scrolls in.

Testing note: Tailwind v4 moves things with the CSS `translate`/`scale` properties, not `transform`, so check `getComputedStyle(el).translate` when verifying a lift. Also, headless Chrome can report `(hover: none)`, which switches off every `hover:` utility; test hovers in a headed (off-screen) window.

### Motion philosophy — the most important lesson from this build
Early hero drafts had a scrolling marquee ticker and a light that traveled up the arc motif on an infinite loop. Both were explicitly rejected by the user as feeling "cheap" and "reasonless." Research (see below) confirmed the instinct: **motion that isn't tied to scroll, cursor, or a one-time narrative beat reads as decorative filler, not craft.** The best scroll/motion design is "invisible until missing," not a perpetual loop running for its own sake.

Rule going forward: before adding any animation, be able to name *why* it moves and *when it stops*. Acceptable categories:
1. **One-time entrance** (plays once on load/mount, then holds still — e.g. the rack-focus headline reveal, the one-time shimmer sweep on "MOVE").
2. **Scroll-tied** (progress is driven by actual scroll position, e.g. `ProofStrip`'s count-up which triggers once on scroll-into-view).
3. **Interaction-tied** (responds to real cursor/hover — the magnetic CTA button, the custom cursor).
4. **Functional affordance** (the scroll-cue bounce at the bottom of Hero — standard, well-understood "more below" signaling, not decoration).

Anything that loops on a timer with no relation to what the user is doing does not meet the bar. This has already caused two rebuilds — don't reintroduce it.

**One sanctioned exception, added 2026-09-05: the toolkit carousel in the About grid's fourth card** (`src/components/ui/ToolCarousel.tsx`). It loops on a timer and is not tied to scroll, cursor or a narrative beat, so it plainly breaks the rule above — **the user asked for it directly, and kept asking until it was right.** It stays. Do not remove it on the strength of this section; the rule has an owner and they've overridden it here. It respects `prefers-reduced-motion` (it holds on its first frame), and React re-renders once per ~2.8s step rather than per frame — if you add another exception, hold it to at least that.

Its shape was specified precisely and got rebuilt once to get there: **not** a planetary orbit around a fixed centre (built, rejected), but tools filing left to right along an arc — in from off the top-left, down into the lit centre where each one **holds for two seconds**, then up and out to the right.

### Copy discipline
Keep hero-level copy to headline + one short line max. A full sentence/paragraph subheadline under the Hero headline was tried and explicitly cut as "too much" — the headline should carry the section. This likely generalizes to other sections: default to less copy, not more.

## Tech stack (and why)

**Next.js (App Router) + TypeScript + Tailwind v4 + Framer Motion.** Chosen over Astro specifically because the site is expected to need coordinated cross-section motion as it grows — Astro's islands architecture isolates state per-island, which fights that; a single React tree doesn't. Framer Motion covers everything from simple reveals to SVG motion paths to scroll-linked transforms, so there was no need to add GSAP on top. Fonts are self-hosted to avoid an extra third-party render-blocking request: Archivo and Special Elite via `next/font/google`, which downloads them at build time and serves them from the site's own origin (Satoshi, self-hosted from Fontshare, was the previous heading face; retired 2026-09-27).

Do not introduce a second animation library (GSAP, native CSS `animation-timeline`/`scroll()`) unless Framer Motion genuinely can't do something — it can do everything used so far, and mixing systems fights the "one coherent motion language" goal. Native CSS scroll-timeline animations (seen in reference components, see below) have real cross-browser gaps (Safari especially) that Framer Motion doesn't have.

### The wordmark, and the footer sign-off (took three attempts — read before touching)

**Two different renderings of the mark, for two different jobs.**

- **`src/lib/wordmark.ts`** — the mark as *stroke geometry*, **measured off `public/ARC Logo.png` on 2026-09-05**, not eyeballed: contours isolated with a local-contrast pass, lines and circles fitted to them, reconstruction checked back against the extracted contours. Rendered by `Wordmark.tsx` (static) and `Loader.tsx` (drawn stroke by stroke with `pathLength`). Use this whenever the mark needs to be **drawn**.
**One mark everywhere, at one weight.** Nav, intro, footer sign-off, OG card and the large icons all render `WORDMARK_PATHS` at `WORDMARK_STROKE_WIDTH`. That weight is **~5% of cap height — deliberately lighter than the logo file's own 9.5%** (`LOGO_MEASURED_STROKE_WIDTH`), asked for by the user on 2026-09-05: flat gold at the measured weight reads heavy on black, where the real sign has a glow to soften it. Change it in one place or not at all. The single exception is the 16px favicon, where a hairline stops rendering; `scripts/generate-brand-assets.ts` scales the stroke up for small sizes only, and is the only place allowed to.

The footer sign-off used to be Satoshi Black — it was replaced with the real mark on 2026-09-05 at the user's request. Full-bleed strokes are ~20px wide at viewport scale, so the "thin strokes vanish at low opacity" problem that justified filled type doesn't apply; the stop opacities were roughly doubled to compensate for a stroke carrying less weight than a solid letterform.

**The R has no vertical stem.** This is the detail the first trace got wrong — it drew a full-height stem down the R's left side, which the real logo does not have. The R is a horizontal top arm, a semicircular bowl, a short return along the bottom of the bowl, and a diagonal leg: one continuous stroke, nothing on the left. Same logic as the crossbar-less A — each letter is identified by what's missing. Along with the stem, the corrected trace changed the proportions (the mark is 3.5:1, not 2.66:1) and doubled the relative stroke weight to 9.5% of cap height. If a rendering of the mark ever looks subtly wrong, check the R first.

Two groupings of the same geometry, and picking the wrong one is visible: `WORDMARK_PATHS` (one continuous path per letter) for anything static — the A's apex is a mitre and the R's corner a join; `WORDMARK_ORDER` (six separate strokes) only for the intro, which has to draw them one at a time. Rendered statically, the split version leaves two butt caps meeting at an angle and notches the apex.

The nav renders the real mark via `Wordmark.tsx`. `<Highlight>` is for emphasised *words* — "ARC Media" in the footer, an emphasised word in a headline — never for the logo itself.

**The footer sign-off failed twice. Both failures are worth keeping:**

1. **Oversized text anchored to its container's bottom under `overflow-hidden`**, intending a bottom-bleed. The type was ~2× the container height, so it actually clipped the **top** — cutting the A's apex, the R's bowl and the C's curve, i.e. exactly the parts that identify the letters.
2. **The stroke geometry, constrained to `max-w-5xl` with side padding, bottom faded to transparent.** This was neither one thing nor the other: it never reached the page edges, so the fade had nothing to dissolve *into*, and it read as a large half-erased outline floating in the middle of the footer.

**The rule that came out of it: a full-bleed element has to actually touch the edges.** Once it does, the page boundary does the cropping and the cut is honest — no fade needed to disguise it. So the sign-off has no max width, no horizontal padding, and no fade-to-transparent.

**Every number in `SignOff` is derived, not eyeballed** — measured from Satoshi Black in the browser: `"ARC"` advances **2.168em** and its cap height is **0.752em**. From those, the font size that makes the natural width exactly fill the viewBox is arithmetic. Estimating it by eye is what caused an 8% horizontal stretch in attempt #3 (visibly over-wide R and C) and, at the corrected size, would have put the glyph tops *above* the viewBox and re-created failure #1. If the heading typeface ever changes, **re-measure rather than nudge**.

Two smaller things that matter: `lengthAdjust="spacing"`, never `spacingAndGlyphs` — if the webfont hasn't loaded the gaps flex, but the letterforms are never distorted. And the fill is a gradient with a **narrow catch of light near the top** rather than a flat tint: a uniform fill at this opacity reads as a dull olive slab, whereas a lit surface reads as metal. Same logic as GoldText's foil treatment — narrow band, never a wide pale plateau.

The sign-off does **not** animate. It's texture, not an event, and the page already closes its narrative with the arc in the Final CTA.

### Full-page Playwright audit — 2026-09-04

Swept every route at 1440×900 and 390×844. No horizontal overflow anywhere, no page errors. Five real bugs found, all now fixed, and four of them are recurring classes worth knowing:

1. **`HowItWorks` clips rendered completely empty.** The waveform bars are sized with percentage heights inside a `flex items-end` container that had **no height of its own** — a percentage height against an auto-height parent resolves to zero. Fixed with an explicit `h-9 sm:h-11`, and `flex-1` on the bars instead of `w-full` (in a flex row, `w-full` makes every child claim the full width and then get squashed). **Any time you see percentage heights, check the parent has a resolved height.**
2. **`FinalCTA`'s arc cut straight through the subline on mobile**, with the travelling light sitting on the text. The viewBox is 1200 wide, so `meet` scales it to about a third on a 390px screen and the arc becomes ~100px tall; `xMidYMax` then pinned that small arc to the *bottom* of its box, landing it in the copy. Fixed by anchoring `xMidYMin`. Not `preserveAspectRatio="none"`, which fits the box neatly but stretches the light and its halo into ellipses. **Check every `preserveAspectRatio` at mobile width — a wide viewBox behaves completely differently there.**
3. **`WhyArc`'s left column was effectively unreadable.** Its scroll-driven opacity multiplied with the text colour's own alpha (`0.3 × text-ivory/50`) and bottomed out near 15% white on charcoal. **Opacity animations compose with token alpha — compute the product, not the animated value.** It's an argument, not decoration, so it needs a legibility floor; the contrast with the right column comes from type size and treatment anyway.
4. **The loud testimonial ran to eight lines** at `text-5xl` inside `max-w-2xl`, reading as a wall of text rather than a pull quote. The loud one now gets its own wider measure.
5. **`/book` opened on "00 / 04" against an empty arc** — looked like nothing had started rather than like you were one question in. Now `(index + 1) / STEPS.length`.

Two things deliberately **not** changed: the generous vertical gaps between sections (that spacing is the cinematic register the brand asked for), and the empty space to the left of the reel's first card (normal filmstrip behaviour at index 0).

One warning is expected and should be left alone: Next reports the first work poster as LCP during an automated scroll-through. ### Loader coordination — and the bug that's easy to reintroduce

The Hero animates on mount, so with an overlay in front of it the whole entrance (including the phone's count-up) would play unseen. `IntroProvider` supplies `useIntroDone()` and the Hero gates on it. This is the coordinated cross-section motion the "Next over Astro, one React tree" decision was made for.

Five things here are non-obvious:

1. **A constant shared between the layout and a `"use client"` module must live in a third, non-client file.** `INTRO_SESSION_KEY` was originally exported from `IntroProvider.tsx`. When the server-rendered `layout.tsx` imported it, Next handed back a client reference rather than the string, and the inline script shipped as `sessionStorage.getItem(undefined)` — silently disabling the entire intro-skip with no error anywhere. It now lives in `src/lib/intro.ts`. This will bite again with any other constant shared that direction.
2. **The once-per-session rule is production-only, and that is deliberate.** `sessionStorage` survives reloads for the entire life of a tab, so in development the intro played once and then never again in that tab — which reads exactly like "the loader is broken" (it was reported as such). With `next dev`, only reduced motion suppresses it. Verified in both modes: dev replays on reload; a production build still plays on a fresh visit, skips on reload, and plays again in a new tab. The trade-off is that **the skip path cannot be exercised with `next dev`** — use a production build to check it.
3. **The skip decision is read from the `data-intro-skip` attribute, not from `sessionStorage` directly.** An inline script in `<head>` sets that attribute before first paint (CSS then hides the overlay, so there's no flash on repeat visits). The attribute is stable for the page load; `sessionStorage` is written the moment the intro reveals, so reading storage live would flip the value mid-animation and cut the dissolve short.
4. **`useSyncExternalStore`, not `setState` in an effect.** This project's ESLint runs React Compiler's `react-hooks/set-state-in-effect`, which is an *error*. Media queries and the skip flag are external stores and must be read that way — see `src/lib/useMediaQuery.ts`. `CustomCursor` was already violating this before any of the new work and is now fixed too.
5. **`<html>` carries `suppressHydrationWarning`, and must keep it.** The inline script sets `data-intro-skip` on `<html>` before React hydrates, so the client DOM legitimately has an attribute the server HTML didn't — React reports a hydration mismatch without this. Exactly the same pattern as a theme script. It suppresses only that element's own attributes and does not extend to children, so it isn't hiding anything else.

### Accessibility

`prefers-reduced-motion` was handled **nowhere** in this codebase before 2026-09-03. It's now covered in three places, and all three are needed:
- `<MotionConfig reducedMotion="user">` in `IntroProvider` — the global Framer Motion guard.
- A CSS `@media (prefers-reduced-motion: reduce)` block in `globals.css` for the plain CSS transitions Framer can't reach.
- Explicit checks where motion is the feature: the loader skips entirely, and `Work` doesn't autoplay video.

Keep this in mind when adding sections — this page is almost entirely motion, so it's a real barrier, not a nicety.

### Problem section — concept selection process (reusable pattern)
When the direction for a section's core creative device was genuinely unclear, the effective approach was: propose 3-5 distinct concepts with reasoning, then **build all of them as real, viewable code** (not just descriptions) on a throwaway comparison route, and let the user pick by actually looking at them live. Concretely: each concept became its own component under a `*-variants/` folder, stacked on a temporary `/​<section>-variants` page with an obvious dev-only label (bright gold bar) above each so it's unmistakable that the labels aren't final UI. After the user picked one, the winner's approach was rebuilt directly into the real section file, and the entire variants folder + temporary route were deleted — no dead code left behind. Use this pattern again for any section where multiple genuinely different creative directions are plausible and worth seeing live rather than debating in the abstract.

### Reusable technique: scroll-driven "word performs its meaning"
Established in `Problem.tsx`: instead of a single whileInView trigger for a whole block, give the specific element that needs a discrete effect its own `useScroll({ target: ref, offset: [...] })` and drive `useTransform` off that element's own scroll position (not a shared/global progress value). This scales cleanly — each effect is self-contained and doesn't need retuning if surrounding copy changes length. One real bug hit and fixed: an effect that dims sibling text while a focal word is centered must have its dim-progress **recover back to 1**, not just clamp at its dimmed value once scrolled past — otherwise everything after that moment stays permanently faded. Fix: use a wider offset range on the *paragraph* (not just the word) covering its full transit through the viewport, and map dim through **3-4 stops** that dip and then return to 1 (e.g. `[0, 0.35, 0.55, 1] → [1, 0.35, 0.35, 1]`), rather than a simple 2-point one-way map.

### Design theory lesson: quiet/loud/rupture, not the same effect four times
First scrollytelling pass on `Problem.tsx` had a real flaw the user correctly caught: every line used the same entrance motion (fade + rise), so even though each word had a *different* payload effect (dissolve / scale / widen), the section still read as one effect repeated four times. The fix, grounded in a few specific principles — worth applying to any future multi-beat scroll section, not just this one:

- **Von Restorff effect (isolation/contrast):** a moment only reads as special if it's surrounded by relative quiet. Don't make every line a spotlight — pick one loud beat and let the others be genuinely quiet (smaller type, less movement, closer to the color of the background) so the loud one has something to contrast against.
- **Motion quality should match meaning, not just the CSS property touched.** "Empty" should barely move (slow, small, entropic). "Alone" should snap in fast then keep growing while lingering (arrival + weight). "Gap" should rupture — a sudden, tight-scroll-window split, not a slow spacing tween.
- **Break the grid for the one moment that means "separate."** `alone.` is pushed off the shared left margin (`ml-8 sm:ml-24 lg:ml-40`) that every other line sits on — visible asymmetry against an otherwise aligned column reads as "wow" precisely because the rest of the layout is orderly.
- **Vary pacing (scroll distance), not just duration.** The loud beat gets a wide scroll window (lingers); the rupture gets a narrow one (snaps). Giving every effect the same scroll-distance-to-resolve is part of what made the first version feel monotonous even with different payloads.

### How the isometric diagram actually works (and the real bugs hit building it)
`ArcSystem.tsx`'s diagram went through a true-3D-projection attempt, a CSS-3D mouse-tilt attempt, and a couple of broken versions of the technique that's actually used now, before landing on something correct. The user also pasted a real DOM dump of a reference isometric diagram mid-build, which settled several things that had been guessed at before. Worth reading this in full before modifying the diagram again.

**The core technique** is a well-known CSS trick, not true 3D and not per-point projection math:
- A flat container gets `transform: rotate(-30deg) skewX(30deg)`. That alone makes a normal square grid look like a proper 30° isometric floor.
- Every node inside it gets the *exact inverse*, `transform: skewX(-30deg) rotate(30deg)`, so its icon/label render as a normal undistorted circle instead of a sheared ellipse, while its *position* (via plain `left`/`top` in the flat, pre-transform coordinate space) still correctly follows the tilted floor.
- **Do not add a `scaleY` correction to either transform.** An early version added one (guessing it was needed for a "true" isometric angle) and it was wrong — verified by hand (matrix multiplication) and empirically (measured rendered badge width/height — with the scaleY term badges came out √3 times wider than tall; without it, exactly 44×44, ratio 1.0). Plain rotate+skewX, no scale, is the exact correct pair.
- Grid lines, connector lines, and zone panels all live in the *same* flat coordinate space as the nodes — that's what makes everything read as one consistent surface instead of separate layers with their own logic.

**Real bugs hit, and the actual fixes** (not just "it looked wrong, we tried something else" — these had identifiable root causes):
1. **A hand-written `transform` string on the same element Framer Motion is also animating (e.g. `animate={{ y: [...] }}`) gets silently fought over** — Framer Motion owns the `transform` property on any `motion.*` component it's animating, so a raw `style.transform` string placed there is unreliable. Fix: put the raw counter-transform on a plain, non-`motion` `<div>`, and put any Framer-animated property (e.g. an idle float) on a *separate* nested `motion.div` that has no competing transform string of its own.
2. **Nested `<svg>` elements don't position reliably.** A version that rendered each connector line as its own `<svg>` (with absolute positioning + `h-full w-full`) *inside* an outer wrapping `<svg>` caused only one of six lines to actually render — nested SVG viewport/positioning behavior is not the same as nesting plain HTML divs. Fix: one single outer `<svg>`, and each line contributes only a `<defs>`/`<path>` (or `<line>`) fragment into it directly — never nest a second `<svg>` inside the first.
3. **`gradientUnits="objectBoundingBox"` (the default) breaks down for vertical or near-vertical lines** — the gradient is defined relative to the path's bounding box width, which is ~0 for a vertical line, making the "flowing highlight" direction inconsistent/backwards depending on the line's orientation. Fix: use `gradientUnits="userSpaceOnUse"` with `x1/y1/x2/y2` set to the line's *actual* start/end coordinates, and scale the `animateTransform` translate distance to that segment's real length (`length * 0.7` worked well) in the direction of its own unit vector. This makes the flow direction correct and consistent regardless of whether a given segment is horizontal or vertical.
4. **Skew shifts x-position proportionally to y**, so elements near the top-left of the flat coordinate space clip against the container's `overflow-hidden` edge more than a flat margin suggests. Fix: shift the whole composition's coordinates right by a healthy buffer (not just a small margin tweak) and re-verify — this took two rounds to get right.
5. **A fixed-pixel-size transformed diagram doesn't responsively scale** — on narrow viewports it just gets cropped by `overflow-hidden`, not shrunk. Fix: wrap the fixed-size transformed content in a separate ancestor that only carries a responsive Tailwind `scale-[...]` class (never combine that with the isometric transform on the same element) — `scale-[0.55] sm:scale-[0.78] lg:scale-[0.8]`. Note the *desktop* scale needed tuning down from 100% too once the diagram moved from a full-width standalone test page into its actual narrower two-column grid slot on the real page — always re-check clipping in the real layout context, not just an isolated test page.
6. **Routing/ordering:** connectors must be simple single-direction (pure horizontal or pure vertical) segments between literally consecutive numbered steps (01→02, 02→03, …) — no multi-corner "loop back" path. A loop-back was tried (curving from the last step back to the first, to visually imply "a system, not a pipeline") and the user rejected it as reading like a confusing direct shortcut between the two endpoints rather than a meaningful return path. Simpler was correct here.
7. **When a fixed-size element doesn't fit its container, the fix is not always "make it smaller."** Shrinking the diagram's scale to stop it clipping inside a grid column was correctly rejected by the user as making it look small/cut-down. The actual fix: stop treating it as a grid column at all — make it a separate absolutely-positioned background layer (full section height, `~60%` width, sitting behind the text via `z-0`/`z-10`), sized as large as the composition actually wants to be, and apply a `radial-gradient` CSS `mask-image` so its edges fade to transparent instead of hard-cropping. A layer that's allowed to bleed and fade reads as intentional and atmospheric; a layer that's scaled down to avoid ever touching its boundary reads as small and cautious. Also: keep the diagram *after* the text in DOM order even though it's visually positioned beside/behind it — `lg:absolute` pulls it out of flow on desktop regardless of DOM position, but on mobile (where it isn't absolutely positioned) DOM order is what determines whether it stacks above or below the heading, and it should stack below.

The pattern used to develop this safely: build comparison variants on a throwaway route (e.g. `/arc-system-variants`), verify shapes empirically (measure actual rendered `getBoundingClientRect()` dimensions and line coordinates via Playwright rather than eyeballing screenshots), then port the winner into the real component and delete the scaffolding route. A private `/reference-diagram` route was also used briefly to reproduce a shared reference's exact DOM structure/technique before adapting it — also deleted once its lessons were absorbed into the real implementation.

## Verification

No test runner exists in this project and it's a visual marketing site, so the check is:

```
npx tsc --noEmit && npm run lint && npm run build
```

All three were clean as of 2026-09-03. Note `npm run lint` was **already failing** before that date (`CustomCursor.tsx`, `set-state-in-effect`); if it fails again, check whether it's your change or that class of rule.

Beyond that: load the page and scroll it. Most of this site's behaviour is scroll-driven and cannot be verified from a build log — the pinned reel, the timeline playhead, the rack-focus quotes and the arc close all need eyes on a real viewport, at both mobile and desktop widths.

**Use Playwright for this, not guesswork.** Two rounds of footer bugs came from designing a visual element without looking at it. Playwright is **not** a project dependency — install it in a scratch directory outside the repo (`npm i playwright`), not here. The machine already has Chrome, and Playwright drives it without downloading its own build:

```js
const browser = await chromium.launch({ channel: "chrome" });   // no browser download
await page.addInitScript(() => sessionStorage.setItem("arc:intro-played", "1")); // skip the intro
```

Then screenshot the element and *read the image*. Two cautions learned the hard way:
- `getBoundingClientRect()` on an SVG `<text>` returns the **em box**, not the glyph ink, so a "top is clipped" check against it produces false positives. Measure painted pixels, or use `canvas` `measureText()` — `actualBoundingBoxAscent` gives the true cap height.
- Font metrics are worth measuring once and hard-coding, rather than estimating per-attempt. That's where the sign-off constants came from.
